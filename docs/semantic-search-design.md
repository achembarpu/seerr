# Local semantic media search

Status: proposal. The existing title index and ordinary TMDB search work independently of this feature. No semantic model or synopsis index is implemented.

## Prerequisite: permission to use the data

TMDB's current [API terms](https://www.themoviedb.org/documentation/api/terms-of-use) prohibit use of TMDB APIs or content in connection with an AI- or machine-learning-based application, including for training. This appears broader than training: embedding TMDB descriptions for retrieval in Seerr needs explicit written permission or a suitable license. Downloading descriptions onto each user's machine does not itself grant that permission. Clarify whether the restriction also covers an AI feature using another source within the same TMDB-powered app before shipping it.

IMDb's [non-commercial datasets](https://data.imdb.com/non-commercial-datasets/) are restricted to personal, non-commercial use and do not contain plot summaries. They can improve title lookup under the applicable terms but cannot supply this synopsis index. Alternatives such as Wikipedia and Wikidata need a coverage study, source-specific attribution and license review, and a decision on the TMDB application-level restriction; they are not an automatic workaround. [Wikimedia's access policy](https://www.mediawiki.org/wiki/Wikimedia_APIs/Access_policy) describes its API and bulk downloads.

The following design is conditional on obtaining rights for a suitable descriptive corpus. Do not start a TMDB synopsis crawl or publish this feature on the assumption that local processing is permitted.

## Product behavior

Allow an administrator to enable semantic discovery independently of title search. On activation, show the model download size, storage and initial indexing progress; download the model, tokenizer and permitted data to the instance. Searches and embeddings run locally, with no external inference service or query sent to the model host. Support pause, resume, failure reporting, retry and disabling; keep normal search usable throughout. The inference runtime is application code packaged with Seerr, whereas model weights, tokenizer and datasets are downloaded assets.

People should be able to search for “feel-good family movies”, “a romantic comedy for the weekend”, or equivalent requests in Tamil or Malayalam. Build documents from descriptions and reliable attributes such as genres, original language, media type and year; omit missing descriptions from semantic indexing, but keep those titles searchable by name. Use titles for identification and disambiguation without letting them overwhelm descriptive text. Resolve “movies like [title]” to a title first and use its document to find related works.

Use a separate discovery section so semantic matches do not displace exact title matches or actors in ordinary search. Combine description/genre keyword candidates and semantic candidates, for example with reciprocal rank fusion; evaluate ranking rather than assuming vector similarity alone works. Apply explicit type, language, year and genre filters to reliable source fields. Text alone cannot guarantee mood, age suitability, exclusions or lead-actor characteristics: do not invent facts or label a result safe for children without suitable evidence.

## Model and runtime

The leading tested candidate is [EmbeddingGemma 300M](https://huggingface.co/onnx-community/embeddinggemma-300m-ONNX), 4-bit ONNX weights at revision `5090578d9565bb06545b4552f76e6bc2c93e4a66`. Its weights are approximately 197 MB plus a 20 MB tokenizer. Follow the model's Gemma terms and verify the conversion's rights. Pin immutable revisions and expected file hashes, verify downloads before atomic publication, and expose download failures and storage requirements. The original Google repository is gated; confirm the chosen conversion and license flow with the model provider rather than implying a conversion removes license requirements.

Use the model's task-specific query and document prefixes and its trained `sentence_embedding` output. Generic mean pooling of the raw hidden states is not equivalent. The model produces normalized 768-dimensional vectors and supports truncation to 512, 256 or 128 dimensions followed by renormalization. Test 256-dimensional signed-byte vectors as a storage candidate: one million raw vectors would occupy 256 MB before database and search-index overhead. Model-weight quantization, dimensional truncation and stored-vector quantization are three separate choices; measure their combined impact on retrieval.

On 1,000 fictional movies from the MIT-licensed [PlotTwist synthetic dataset](https://huggingface.co/datasets/razsarusi/plottwist-movies), eight short English, Tamil and Malayalam discovery queries produced 22 of 40 top-five results matching both the dataset's genre and a selected tone with Gemma 4-bit, versus 10 with multilingual E5 small 8-bit and 8 with Granite multilingual R2 8-bit. Gemma 4-bit and 8-bit shared 7–10 of their top ten results per query. These are synthetic, automatically assigned labels and a very small smoke test, not a real-world relevance benchmark or evidence of content safety. The Gemma model still ranked a synthetic dark comedy first for the family-night requests. Run a larger human-judged, held-out evaluation before making a quality promise.

[EmbeddingGemma 2](https://huggingface.co/onnx-community/embeddinggemma-2-ONNX) is a newer candidate with a 175 MB 4-bit text model and a 32 MB tokenizer; its vision and audio models are unnecessary here. Its developer reports similar multilingual text benchmark scores to the first generation. In the same synthetic smoke test, its 4-bit text model matched genre and tone for 21 of 40 top-five results and embedded 1,008 texts in 23.7 seconds, versus 22 of 40 and 9.7 seconds for the first generation on the same Mac with native ONNX. This small test favors the first generation but is not representative of every device or catalog. Compare both on the held-out catalog and target runtime before fixing the shipped model.

A direct ONNX Runtime Web/WASM plus JavaScript tokenizer prototype ran the first-generation model locally on the development Mac and produced a normalized embedding comparable to native ONNX for one query. The simple prototype peaked around 1.1 GB RSS, including model-loading copies; its memory usage is not yet suitable as a promise for small NAS devices. ONNX Runtime documents [single-threaded WASM in Node](https://onnxruntime.ai/docs/get-started/with-javascript/web.html). Benchmark and reduce copies, run inference in a bounded worker, and test the actual Alpine/musl images and supported CPU architectures. A native backend is optional only if its package and architecture support are verified; it must not introduce a separately managed service. Report unsupported platforms clearly and leave title search available.

## Index and refresh

Store semantic records and source identifiers separately from the title index, with a document hash, source/language, model revision and document-format version. Write short transactions, publish only completed batches, and resume from checkpoints after interruption. Hash the relevant source fields and re-embed only when those fields or the model/document version change. Deletions remove corresponding vectors. Give interactive query inference priority over background indexing, limit CPU and memory, and make the index resumable across restarts.

Start by evaluating [sqlite-vec](https://alexgarcia.xyz/sqlite-vec/), a pre-1.0 SQLite extension that can keep vectors in the existing local architecture, with int8 and structured-filter support. Benchmark exact or quantized retrieval against float32 exact search for recall, latency, disk and memory at realistic catalog sizes, including ARM and Alpine. Only add an approximate-nearest-neighbor index if the measured latency requires it; test filtered recall, updates and recovery before committing to an extra native dependency. Avoid assuming that model size equals runtime memory or that smaller quantization always preserves ranking.

If TMDB grants the required rights, its [daily ID exports](https://developer.themoviedb.org/docs/daily-id-exports) provide IDs and limited attributes, not plot descriptions. Bootstrap requires a separate description source or many paginated/detail requests; partition Discover requests where needed and respect provider limits. Prioritize locally requested and popular titles, then backfill in the background. Seerr currently embeds a shared TMDB API key, so per-instance throttling alone does not bound aggregate demand across installations. Obtain an approved bulk feed, an appropriate key arrangement and an aggregate load budget before deploying a full-catalog crawl.

For incremental refresh, use [TMDB change lists](https://developer.themoviedb.org/docs/tracking-content-changes), fetch only changed descriptions, and skip embedding when their content hash is unchanged. Change-list windows cover at most 14 days, so a longer outage needs reconciliation. Compare with the daily ID export to remove deleted titles. For any other licensed source, use its own bulk snapshot, incremental feeds and license requirements instead of assuming this TMDB procedure applies.

## Release checks

Create a held-out, human-judged set of ordinary discovery queries in the relevant languages, including cross-language descriptions, similar-title queries, uncommon films and explicit filters. Measure relevance at the top results, filter violations, coverage and quantization recall against a full-precision baseline. Test interrupted downloads, disk exhaustion, model upgrades, incremental changes, cancellation and removal. Measure first-index time, incremental cost, query latency, peak RSS and disk on representative x64 and ARM installations under real container limits. Ship only when the license, coverage, quality, resource limits and platform checks are satisfactory.
