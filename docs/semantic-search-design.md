# Local smart discovery

Status: researched design, not an implemented feature. The existing optional title index and ordinary TMDB search remain separate. This proposal unifies natural-language discovery, similarity, filtering, personal recommendations and optional conversation behind one local retrieval service.

## The data-rights decision

Generating embeddings is inference: the embedding model's weights do not change. It is not model training. However, [TMDB's API terms](https://www.themoviedb.org/documentation/api/terms-of-use) prohibit use of TMDB APIs or content **in connection with** an AI- or ML-based application, including training. That wording is broader than training and appears relevant even when the model and index run locally. Obtain written permission or a suitable license covering Seerr, embedding, retrieval, recommendations and any chat integration. It is also unclear whether an AI feature using only another source is permitted in the same TMDB-powered application. Do not present isolating the data or locally downloading it as a confirmed exemption.

**Wikipedia text joined with Wikidata facts** is a candidate open synopsis source, not a proven best source for Seerr. The previous recommendation was premature: we verified a page and identifier, not representative synopsis coverage or recommendation quality. Wikipedia text is generally CC BY-SA, subject to page-specific exceptions; preserve page/revision URLs, attribution, license notices and modification information, and meet applicable share-alike obligations. Wikidata structured statements are generally CC0. Check the actual content and provider [reuse requirements](https://foundation.wikimedia.org/wiki/Legal:Wikimedia_Developer_App_Guidelines/en). Public availability and download-on-enable do not remove either source's license conditions or TMDB's separate API terms.

This is a workable data source, not a proven complete catalog. We verified that [Maaveeran (2023)](https://www.wikidata.org/wiki/Q118465261) links to English, Tamil and Malayalam Wikipedia pages and carries an IMDb and TMDB identifier. The English article contains a detailed plot, but one article does not establish coverage for lesser-known titles or TV, and many articles may offer only a short lead or no usable plot. Wikipedia plot sections may be absent, very long, contain spoilers, or vary by language. Never expose the full plot through explanations or chat without a spoiler opt-in.

[TVmaze](https://www.tvmaze.com/api) is another candidate for TV series: its public API includes descriptions under CC BY-SA with attribution and share-alike requirements. It is not a movie catalog, and its actual coverage needs measurement. Provider-specific rights still need checking in the context of a TMDB-powered application.

[IMDb's non-commercial datasets](https://data.imdb.com/non-commercial-datasets/) provide titles, genres and ratings, not synopses, and are limited to personal, non-commercial use. The existing IMDb title index is therefore not a substitute for licensed descriptive text. Consider ratings only within their provider's permitted terms. Third-party datasets that mix TMDB data with Wikipedia, such as [this research dataset](https://huggingface.co/datasets/NiklasAbraham/MoviePlotEmbeddingsDataset), do not eliminate the TMDB restriction merely because they are downloaded elsewhere.

## Data bootstrap and updates

1. When an administrator enables smart discovery, start with the user's existing library, requests and watchlist. Resolve IMDb or TMDB identifiers to Wikidata items using exact Wikidata external-ID statements, then obtain Wikipedia sitelinks and extract the lead and plot/premise sections. Wikimedia's [statement search](https://www.mediawiki.org/wiki/Help:Extension:WikibaseCirrusSearch) supports exact external-ID lookup. Do not fuzzy-join an uncertain title to a different film; record ambiguous and missing matches.
2. Batch entity and article reads where supported; identify the client, cache misses and revisions, limit concurrency, honor rate limits and `Retry-After`, and add jitter. Download only allowed source assets. Do not send the user's search queries to Wikimedia. Index requested and local titles first, then backfill catalog candidates in the background.
3. A broad ready-to-download film/TV corpus remains a release dependency for catalog-wide discovery. [WikiPlots_EN](https://github.com/piperandrew/Wikiplots_EN) reports 116,419 visual-media plots from its July 2026 run, including films, TV, animation and games; it is an extraction pipeline, not a verified current downloadable film-only feed. Its full rebuild requires an approximately 26.5 GB English Wikipedia dump and substantial processing. Do not impose that download on every homelab or claim global coverage from a library-first bootstrap. A practical broad release needs a maintained, compressed, versioned and attributable Wikipedia/Wikidata-derived snapshot published separately from the binary, or a genuinely suitable existing feed. Selecting and hosting such a snapshot remains open work; do not silently create a centrally managed production service.
4. Refresh resolved entities and linked pages incrementally, use revision IDs/content hashes to avoid unchanged work, and re-embed only changed documents. Poll bounded batches with backoff; revalidate old misses and removed pages periodically. Resume checkpoints after interruption and retain the last usable index. Coverage, stale sources, progress, disk use and failures must be visible.

All extraction, normalization and vector generation run on the user's instance. If a project-published snapshot is used, its distribution and CC BY-SA obligations must be explicitly handled; “not bundled in the binary” does not mean “not distributed.”

## Embedding model and inference engines

Recommend **[Bekko embedding v1 a8m](https://huggingface.co/hotchpotch/bekko-embedding-v1-a8m)** as the first model to validate. It is MIT-licensed, multilingual, has 106M total parameters but only 7.7M active transformer parameters, and outputs 384-dimensional vectors. Its author's MMTEB multilingual retrieval results and benchmarks are promising, but its model card says submission through the official [MTEB leaderboard](https://huggingface.co/spaces/mteb/leaderboard) pipeline is pending; treat those scores as author-reported. Language-specific quality still needs testing. In the same 1,000 synthetic descriptions and eight discovery queries used previously, Bekko matched the automatically assigned genre and tone in 15 of 40 top-five positions, versus 22 for Gemma 4-bit and 10 for E5 small; these few synthetic labels do not predict production relevance. E5 small is faster than EmbeddingGemma but scored lower on our discovery smoke test; [EmbeddingGemma](https://huggingface.co/onnx-community/embeddinggemma-300m-ONNX) remains a useful higher-cost quality comparison, not the default based on the current evidence.

For native CPU inference, test the 118,639,520-byte [Q8 GGUF model](https://huggingface.co/hotchpotch/bekko-embedding-v1-a8m-GGUF) at revision `4acacdea60b9393ae247a6ebf5b5707938c9755b` (SHA-256 `0b0214214287e90ffb98ffb47e1071e5b193fb420d1d99b2ec8aab0ebb507fc0`) with a bundled [llama.cpp](https://github.com/ggml-org/llama.cpp) runtime. Use its native CPU backend by default and choose a validated Metal, CUDA or Vulkan backend when available. Download only the selected model after opt-in; embed the inference runtime as application code, not a manually operated external server. Backend selection must use explicit capability checks and fall back to CPU on recoverable accelerator failure. The GGUF conversion metadata identifies a compatible tokenizer from the Gemma 2 repository and documents leading/repeated whitespace limitations. Verify that tokenizer's provenance and applicable terms for this conversion, and test tokenization across the supported languages before shipping; the model card's MIT label alone does not settle every bundled component.

WASM was investigated as a portability prototype, not selected for performance. Native CPU plus GPU backends is a better starting point. The model author reports [OpenVINO](https://huggingface.co/hotchpotch/bekko-embedding-v1-a8m) faster than ONNX on their CPUs; consider it as an optional backend after testing its packaging and output equivalence. Our OpenVINO Node prototype aborted with `Xbyak::Error` in this environment, so it is not validated. Neither OpenVINO nor a native binding should be assumed to work on the project's Alpine/musl image without an actual build and test. The current release pipeline targets Linux amd64 and arm64; define support for any other architecture only after testing it.

On this development Mac, the CPU-only `llama-embedding` executable processed 1,008 short synthetic descriptions and queries in 2.53 seconds including process startup, with 429 MiB maximum process RSS and two threads. Its English, Tamil and Malayalam vectors had cosine similarity 0.9996–0.9998 to the native ONNX export; top-ten neighbors were identical for seven of eight sample queries and differed by one result for the eighth. This is process memory, not total Seerr container memory; it includes model loading but excludes Seerr's Node process and existing index. The equivalent prototype using native ONNX and either JavaScript or Rust tokenizer reached roughly 770–840 MiB; using a native tokenizer alone did not solve the large vocabulary's memory cost. All these numbers are a single Mac experiment, not NAS guarantees.

Use bounded batches and context, memory-mapped model weights where supported, a long-lived inference worker, two CPU threads as an initial configurable budget, and query priority over indexing. Test lower memory limits, idle unloading, concurrent requests and input-length limits. Measure the packaged container's full resident and cgroup memory, not just model-file size. Verify backend changes against a canonical vector set; never mix incompatible model versions or vector spaces in one index.

## Quantization and ranking

Weight quantization and stored-vector quantization are independent. The Bekko GGUF author's [comparison](https://huggingface.co/hotchpotch/bekko-embedding-v1-a8m-GGUF) found Q4 only 1.9% smaller than Q8 and slower on a Pi 5 because of tensor fallbacks; avoid assuming that a lower bit count means lower memory or better speed. Q8 is the initial CPU candidate; compare accuracy and throughput on target machines.

Store normalized 384-dimensional vectors as signed int8 initially: 384 raw bytes per title, roughly 38.4 MB for 100,000 or 384 MB for one million, excluding SQLite, text, metadata and index overhead. Evaluate [sqlite-vec](https://alexgarcia.xyz/sqlite-vec/) with filtered exact vector search; add a separate approximate index only if target-size measurements justify it. Record scales/normalization consistently and validate quantized ranking against the full-float baseline.

Bekko supports 256, 128 and 64-dimensional Matryoshka truncation. In a tiny synthetic test of eight queries over 1,000 descriptions, 256-dimensional int8 vectors retained 6–10 of the full 384-dimensional top ten per query; 128-dimensional int8 retained 4–8, and 64-dimensional floats retained zero of ten for one Tamil query. Binary vectors alone performed worse. These are overlap measurements, not human relevance judgments; they make 64/128/binary unsuitable as an untested default. A binary shortlist followed by int8 reranking may be useful, but the sample is too small to justify shipping it. Pick the smallest representation that meets measured multilingual relevance and latency targets rather than maximally compressing by default.

## One discovery service, multiple experiences

Each record combines a licensed description, genre and subject tags, original language, country, year, runtime, cast/director where sourced, media type, availability and provenance. Omit unknown fields instead of inventing them. Keep external ratings and vote counts separately by source; use confidence-aware ranking and explicit minimum-rating/minimum-vote filters, never pretend scores from different providers are interchangeable. Apply library availability, watched/unwatched, year, language and other hard constraints before ranking, with per-user permission checks.

Generate candidates from local keyword search, semantic similarity, explicit similar-title seeds and eligible recommendations; deduplicate by verified identifiers, combine ranked lists and diversify the results. Use user-selected likes/dislikes and opt-in watch history for personalization; keep those profiles per user, explain why a title was suggested and provide a reset. Existing Seerr code already exposes TMDB recommendations and similar-title endpoints; TMDB says its [similar endpoint](https://developer.themoviedb.org/reference/movie-similar) uses genres and plot keywords. Blending TMDB recommendations or metadata into this AI feature is conditional on the rights decision above. Treat a missing recommendation, rating or synopsis as unknown, not negative.

Conversational discovery is an optional second model and download, not a capability of embeddings. Use the same local inference engine where supported, with a small instruction model as a candidate; its CPU memory and quality are a separate budget. The model translates a request to a constrained search/filter operation, asks clarifying questions when needed, and explains only retrieved, permission-checked records. The application validates filters and title IDs; the model never writes SQL, invents titles, makes requests, changes settings or performs actions on its own. Treat descriptions as untrusted data, not instructions. Default to local processing, keep chat history user-controlled, and never send it to a remote provider without explicit opt-in. A small chat model's multilingual and tool-use quality must be tested rather than assumed.

## Release gates

- Resolve TMDB's terms for the whole feature and any blended feeds; document Wikipedia attribution, source licenses and actual coverage.
- Provide a usable snapshot/bootstrap strategy and test restart, deletion, refresh, failures, quotas and model upgrades. Measure coverage over representative local and catalog titles, especially Tamil, Malayalam, recent titles and TV.
- Evaluate ordinary human-judged requests, negative filters, similarities, rating thresholds, multilingual queries and short descriptions. Compare keyword-only, Bekko, E5 and EmbeddingGemma; measure relevance and wrong-constraint rates, not just model leaderboard averages or quantized-vector overlap.
- Test real Docker builds and inference on Alpine amd64 and arm64, CPU budgets and accelerators where supported, including full-container peak memory and query latency while indexing. Docker was unavailable in this research environment; no container or NAS benchmark has been performed.
- Test conversation separately for unsupported claims, spoiler leakage, user isolation, prompt injection through descriptions, permission checks and safe handling of unknown metadata. Chat must remain optional.
